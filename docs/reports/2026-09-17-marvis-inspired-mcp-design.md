# Marvis-inspired Python MCP: evidence before action

_Date: 2026-09-17. Status: product-design recommendation; documentation contracts verified, tenant behavior not tested._

**Decision:** build a small, read-first Mist investigation assistant, not a Marvis clone. Follow the loop **observe -> correlate -> recommend -> explicitly authorize -> act -> refresh and verify**. A runnable server, registered tools, or mocked responses are not evidence that an integration works against Mist.

The initial research used eight first-party source documents/specifications. The follow-up below independently inspects a published SDK, its license, and ordinary vendor documentation; SDK authorship is distinguished from official vendor support. No Mist credentials, tenant requests, device operations, or model builds were used. The prototype's fabricated-success behavior is supplied context, not an independently repeated audit; factory implementation is outside this document's scope.

## What to borrow from Marvis

| Operating pattern | Documented behavior and design implication |
| --- | --- |
| Observe and correlate | Marvis scans statistics and events for user-impacting wired, WAN, and wireless issues, covering pre- and post-connection experience. Marvis Actions **does not replace real-time alerts**. The MCP should join observations, not rename every alarm a root-cause diagnosis. [Juniper: back-end operations](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/topic-map/marvis-actions-backend-operations.html). |
| Prioritize and recommend | Actions expose issues, affected infrastructure, and recommended remedies so operators can prioritize. The documented Missing VLAN example identifies affected APs and switch ports and recommends adding the missing VLAN configuration. The MCP should similarly show evidence and a specific recommendation, but distinguish a vendor-reported finding from its own hypothesis. [Juniper: Marvis Actions overview](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/concept/marvis-actions-overview.html). |
| Use bounded authority | Driver-assist requires operator intervention; selected self-driving actions can remediate under granted organization/site permissions. This is not unrestricted automation. There are documented defaults/exceptions: Port Stuck and Intermittent WAN Connectivity are enabled by default; DFS Optimization cannot be disabled. These vendor permissions do **not** authorize a custom MCP to write. [Juniper: self-driving actions](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/concept/self-driving-marvis-actions.html). |
| Validate, then close | `Resolved by User` and `Marvis Self Driven` are distinct from `AI Validated`. Marvis checks that the issue no longer occurs during its validation period; recurrence can reopen it. A successful HTTP command or manual status change is therefore not proof of recovery. The MCP must not assign itself Marvis's `AI Validated` status. [Juniper: lifecycle and status definitions](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/concept/marvis-actions-overview.html). |

**Licensing boundary:** Juniper documents Marvis for Wireless, Wired, and WAN subscriptions **per device, in addition to the corresponding base Assurance subscription**. API access is not evidence of Marvis entitlement. Do not promise Marvis findings for an unlicensed tenant, or infer a particular endpoint's licensing behavior from UI availability. [Juniper: subscriptions](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/ref/marvis-subscriptions.html).

## Bounded product workflow

The following are **MCP design decisions**, not claims about proprietary Marvis algorithms.

1. **Select real scope.** Load privileges, list sites for an authorized organization, and let the operator select one site. Restrict this first implementation to APs and wireless clients. Resolve every target from returned IDs; a privilege or inventory failure blocks dependent work rather than selecting a sample site.
2. **Observe one incident window.** Collect AP snapshots, wireless-client statistics, and alarms using an explicit 15-minute incident window for the time-filtered reads. Store request time separately from telemetry `last_seen`. Retain raw record references, applied filters, and pagination/limit coverage. A missing field remains unknown, not zero; an empty collection is only an empty result for that query.
3. **Correlate without overclaiming.** Within the same site and compatible observation times, join `alarm.aps[]` to AP `mac`, then client `ap_id` to AP `id` or normalized `ap_mac` to AP `mac`. Conflicting IDs or stale associations are unresolved evidence, not forced matches. Display source severity, recurrence and the number of actually observed associated clients to prioritize; do not label every associated client impacted. AP/client correlation fields are documented in the [AP schema:104439-104815](https://github.com/mistsys/mist_openapi/blob/9548e1f4bd9e3b31f2423b8a43b69dd7f64794e7/mist.openapi.yaml#L104439-L104815) and [wireless-client schema:109790-110008](https://github.com/mistsys/mist_openapi/blob/9548e1f4bd9e3b31f2423b8a43b69dd7f64794e7/mist.openapi.yaml#L109790-L110008).
4. **Recommend an evidence-backed next step.** For example, if a returned Marvis `bad_cable` alarm identifies an AP, show that vendor finding beside its AP/uplink observations and recommend inspecting the cable and the LLDP-reported upstream port, if present. If there is only a disconnected AP, say "AP or upstream connectivity issue; root cause undetermined" and recommend power/uplink inspection. Never infer a VLAN, switch port, device count, or successful diagnostic test that was not observed. A restart is not a default cure for cabling or authentication faults.
5. **Keep execution separate.** Default tools are read-only. An optional restart requires a displayed proposal containing the exact site/device, evidence references, disruption warning, and verification criteria. Require deliberate approval from the operator through a trusted host interaction, bound to that proposal, target, and parameters; an LLM-supplied `approved=true` is insufficient. Approval expires and is single-use. Refresh the target before execution, verify it is an AP in the approved site, and record who approved and what was sent. No approval means **no POST**.
6. **Refresh and verify.** Re-read the same device and original alarm window plus the subsequent interval; compare against the preserved baseline. A restart `200` means only `command_accepted`, not `rebooted` or `fixed`. Look for advancing telemetry, connected state, restart-consistent uptime where available, and explicit resolution of the original alarm or a demonstrably cleared symptom. As an initial MCP policy, require two fresh observations at least 60 seconds apart within a 10-minute deadline; this is **not** a Mist SLA or Marvis validation time. Expired search windows, absent records, stale telemetry, failed reads, or missing reboot evidence cannot prove recovery. Report `verified_recovery`, `unresolved`, or `inconclusive`, with the exact predicate and window; never claim Marvis AI validation.

**Result contract:** every tool returns an explicit outcome (`ok`, `partial`, `error`, `approval_required`, `command_accepted`, or a verification outcome), data origin (`live` or `simulated`), and evidence references. Each evidence reference identifies method/path, sanitized query, site/device, fetch time, source timestamp if present, and record ID/JSON pointer. Recommendations name their supporting evidence and label `vendor_reported`, `observed`, or `hypothesis`; a documentation URL proves an API contract, not a tenant diagnosis. Simulation is an explicit separate mode, never a fallback after live failure. Preserve useful partial evidence while enumerating failed sources; do not expose credentials or unnecessarily export client identity.

## Error and rate-limit behavior

Mist documents `400` as incorrect syntax/payload, `401` as failed authentication, `403` as insufficient privilege, `404` as a missing endpoint or resource, and `429` as exceeding the 5,000-calls/hour threshold. Its published error examples use a JSON `detail` field, e.g. `{"detail":"Authentication credentials were not provided."}` for `401`; do not require every failure to have that exact body. [Juniper: HTTP response codes](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/rest-api-http-response-codes.html); [pinned response schemas/examples](https://github.com/mistsys/mist_openapi/blob/9548e1f4bd9e3b31f2423b8a43b69dd7f64794e7/mist.openapi.yaml).

The first-party rate-limit page states **5,000 calls per hour, reset at the hourly boundary**; the response-code documentation describes the token reaching that threshold. These sources do not establish independent allowances for every token, guaranteed rate-limit headers, or a guaranteed `Retry-After` header. Do not multiply tokens to assume more quota. [Mist: API rate limiting](https://www.mist.com/documentation/api-rate-limiting/).

Recommended handling: cache inventory, bound page counts/concurrency/polling, and reserve quota for verification. Surface `401`/`403` immediately without substituting fixtures or blindly retrying. Preserve HTTP status and sanitized error detail; distinguish malformed JSON, transport failure, and upstream HTTP failure. For `429`, honor a valid `Retry-After` if supplied; otherwise use bounded backoff and report rate-limited/incomplete work. Never automatically replay a restart after a timeout: the action's execution state is unknown, so observe first and require a new deliberate decision before another write.

A real response derives every ID/count from captured responses. With no authorized tenant run, report **live verification not performed**, even if fixture tests and server startup pass. |
| All tools receive HTTP 401 | Every tool that needs failed API evidence reports an authentication error, not success, fabricated devices, remediation, or verification. Dependent diagnosis/write tools stop; no fallback HTTP requests or restart occur. |
| Partial failure | AP read succeeds but alarms fail or a later inventory page fails: return `partial` with successful evidence and explicit missing coverage. Do not say "no alarms", "site healthy", or report a complete inventory. A client result at its limit cannot establish an exhaustive affected-client total. |
| Evidence-linked correlation | Fixture AP MACs/client AP IDs match only inside the selected site and time context. Contradictory or missing associations yield uncertainty. The recommendation cites actual records; unobserved topology and root causes are not invented. |
| Approval-required write | Missing, expired, reused, wrong-target, or model-generated approval results in zero POSTs. Valid operator approval permits only the exact single-AP restart with the documented body, not arbitrary URLs or batch operations. |
| Command accepted, not verified | A mocked restart `200` without refreshed observations returns `command_accepted` and pending/inconclusive verification. No synthetic job ID, `fixed=true`, or `AI Validated` claim is produced. A timeout reports unknown execution state and is not automatically replayed. |
| Post-action verification | Fresh evidence meets the defined predicate across two observations at least 60 seconds apart within 10 minutes before reporting `verified_recovery`. Old `last_seen`, merely disappearing alarms, an open original alarm, recurrence, or failed refresh cannot pass; show `unresolved` or `inconclusive` as appropriate. |
| Error/limit fidelity | Inject `400`, `403`, `404`, `429`, malformed bodies, and transport failures. Preserve their distinct meaning. Pagination follows documented mechanisms; retry budgets terminate and do not change origin to simulated. |
| SDK boundary | Use hand-authored SDK-result fakes, not OpenAPI-derived fixtures. Cover returned non-200 responses, malformed JSON leaving `{}`, absent status, omitted false-valued filters, initialization failure, hung transport, and 429 retry behavior. Do not enable restart or claim a bounded live workflow until the transport controls are demonstrated. |

## Non-goals, unknowns, and build handoff

**Non-goals:** cloning proprietary Marvis intelligence; full wired/WAN/MSP operations; a universal health score; undocumented UI APIs; autonomous remediation; changing Marvis permissions; acknowledging/closing alarms as a substitute for fixing them; firmware/configuration changes or batch restarts.

**Not established without authorized tenant evidence:** per-endpoint entitlements and tenant coverage, all UI-to-API mappings, telemetry refresh/retention guarantees, complete client pagination, global quota aggregation, and actual command-to-device behavior. The specification is documentation, not proof of deployed response fidelity. Missing Marvis data alone does not prove either a licensing failure or a healthy network.

**Native SkyN3t build input:** use only the SDK-first call map and integration requirements, not the historical OpenAPI contracts. Build one read-first `diagnose_site` workflow over the five `mistapi` read functions; return evidence-linked observations, recommendations, and honest partial errors. Keep restart disabled until its payload, approval path, transport bounds, and post-action verification are independently established. Consuming the MIT package is the license-permitted candidate route; **official vendor support has not been verified**. Delivery must distinguish **fixture-validated prototype**, **live read-verified integration**, and **operator-approved action verified**; passing one level must never imply the next.
