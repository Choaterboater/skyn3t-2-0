# Mist API and feature parity: bounded comparison

**Research date: 2026-09-18. Local findings incorporate the parent's completed installed-MCP and source inspection; no live tenant was tested.**

**Scope note:** The initial comparison below concerns the two earlier Marvis
artifacts. The later **Richer-build delivery findings** and **Final independent
acceptance** sections describe the subsequently generated proactive MCP.

**Conclusion:** These MCPs cover a narrow, useful read-only operational slice of Mist, not broad Juniper API or Marvis feature parity. **The rebuild is not a feature superset of the original:** it removes standalone alarm search and public paging/cursor/absolute-window controls, as detailed in the parent-verified comparison below. Juniper documents configuration and provisioning APIs, organization inventory, SLE/Insights analytics, and event integrations beyond the five implemented GET routes. Marvis adds conversational troubleshooting and permission-controlled remediation. Importantly, a generic alarms route can carry some Marvis-generated findings; "no dedicated Marvis endpoint" does not mean "no Marvis-derived data." [REST overview](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/restful-api-overview.html); [SLEs and Insights APIs](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/api-mist-metrics.html); [Marvis alarm delivery](https://www.mist.com/documentation/monitoring-mist-with-webhooks/).

## Operational qualifications

**Authentication and region:** Juniper documents user-bound and organization-bound API tokens, and its usage guide shows `Authorization: Token <token>`. Choose the API host for the organization's cloud region; `api.mist.com` is not a universal tenant host. The REST overview also lists external OAuth2 and labels login-credential authentication for deprecation in September 2026; this review does not establish whether every region has completed that transition. It documents a 5,000-call/hour limit, without enough detail here to assert a universal per-user/per-token accounting rule. [Token scope](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/task/create-token-for-rest-api.html); [token syntax](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/task/use-mist-api-reference.html); [regional-host guidance](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/topic-map/api-endpoint-url-global-regions.html); [authentication and rate limiting](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/restful-api-overview.html).

**Time ranges and changing interfaces:** The SLE guide says data updates every ten minutes and recommends explicit one-hour query intervals with hourly polling. It also announces replacement of metric/classifier `summary` endpoints by `summary-trend` in an upcoming 2026 release. That is a documented migration warning, not confirmation of its current deployment status. A future SLE integration must verify the active contract rather than copy older examples. [SLE monitoring and deprecation notice](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/api-mist-metrics.html).

## Marvis: product capabilities versus REST exposure

**Conversation:** Juniper's enhanced Conversational Assistant documents natural-language questions, telemetry analysis, multiple workflow agents, diagnostic tools, likely-root-cause/impact analysis, corrective recommendations, and follow-up questions. Examples span wireless authentication/roaming, switch-port profiles, and VPN-path failures. These are product capabilities, not proof of a public conversational-query endpoint or of local access to Marvis reasoning. [Enhanced Conversational Assistant](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/concept/marvis-conv-assistant-enhanced.html).

**Actions:** The Actions dashboard presents organization-wide ongoing issues and recommended actions. Juniper distinguishes driver-assist from self-driving corrective measures: wireless examples include AP firmware compliance and DFS/capacity optimization; wired examples include stuck-port bouncing, missing-VLAN corrections, and rogue-DHCP/L2-loop port mitigation; WAN examples include SRX **backup-partition** Junos synchronization and specified uplink connectivity remediation. Self-driving depends on organization/site permissions and action-specific restrictions/defaults, **not a universal per-action approval requirement**. Juniper also documents post-remediation AI validation. [Actions dashboard](https://www.juniper.net/documentation/us/en/software/mist/marvis/mist-aiops/topics/concept/marvis-actions-overview.html); [self-driving scope, permissions, and validation](https://www.juniper.net/documentation/us/en/software/mist/mist-aiops/topics/concept/self-driving-marvis-actions.html).

**Important distinction:** Public delivery of some Marvis findings is established: the official webhook guide ties Marvis alarm events to Marvis Actions and describes `details.state` values `open` and `validated`; the pinned alarm-search interface documents `group=marvis`. Neither establishes a conversational prompt API, complete dashboard-equivalent retrieval, or programmatic remediation execution. Those contracts remain **unverified, not proven absent**. Do not equate webhook `details.state` with every REST response's status shape without checking that specific interface. [Marvis webhook states](https://www.mist.com/documentation/monitoring-mist-with-webhooks/); [alarm-search interface](https://github.com/tmunzer/mistapi_python/blob/66a57a64f2cae222da36c3a45a639c2a70c54156/src/mistapi/api/v1/sites/alarms.py#L160-L244).

## Why 97/100 is not 97% Juniper feature coverage

The supplied **97/100 is a narrow-build review + proof grade**, not a vendor-parity score or production certification. The reported 11 passing offline wire tests per application can support the tested request/response behavior under fixtures; they do not establish live-tenant correctness, every documented filter/response variant, scale/pagination completeness, regional compatibility, subscription availability, or equivalent vendor analytics. The parent-confirmed removed controls and first-page/100-record collection limits remain relevant regardless of that grade.

Feature breadth, implementation depth within a route, operational correctness, and proprietary-AI equivalence are different measures. Even a perfectly implemented read-only brief intentionally omits configuration and remediation. Conversely, counting routes would underrepresent metric-driven SLE/Insights capabilities and conflate an API wrapper with the underlying service. [Juniper's metric/classifier explanation](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/api-mist-metrics.html).

The rebuild is not a feature superset of the original, and neither demonstrates broad Mist API or Marvis parity." No authoritative, current endpoint-count denominator was established in this bounded review, so **no coverage percentage is assigned**.

### Promptless worker and unsupported/deferred scope

**Local worker contract:** Poll only configured, authorized organizations/sites using token authentication and a configured regional host; never discover credentials interactively. Intersect configured allowlists with understood privilege/membership evidence; unknown or incomplete scope stays blocked/partial, not silently broadened. Budget all pages/retries against the polling ceiling, back off on 429/transient failures, and preserve incident state on collection failure. Juniper now explicitly documents Basic Authentication deprecation effective September 2026; use tokens, not a login fallback. [Current authentication notice](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/addition-restful-documentation.html). SLE polling should follow the documented hourly explicit-window recommendation, not every AP poll. [SLE guidance](https://www.juniper.net/documentation/us/en/software/mist/automation-integration/topics/concept/api-mist-metrics.html).

Persist polling checkpoints, incident/evidence identity, deduplication, and outbox state transactionally in SQLite. Use stable local identities incorporating organization/site/entity/finding type; retain vendor IDs when available rather than assuming every returned ID identifies an incident across polls. Replay/restart must not duplicate a transition/outbox item. AP offline and unknown are distinct; vendor alarms remain attributed vendor findings, not local Marvis inference. **Fresh recovery requires a subsequent authorized, successful, sufficiently fresh positive observation for the same entity or an understood explicit vendor resolution signal.** A recent fetch alone does not prove cached telemetry freshness. Empty pages/windows, missing entities, unassigned inventory, acknowledgments, expired alarms, truncation, or failed polling are not recovery. Without trustworthy freshness/resolution semantics, retain `recovery_unconfirmed`. Mist writes/remediation remain disabled; external outbox delivery needs an explicitly authorized destination.

**Deferred/not claimed:** Org-wide SLE overview, Marvis settings, conversational Marvis, Actions execution, switch/WAN-specific diagnostics beyond the qualified type-filtered reads, automatic REST-alarm resolution normalization, and fully normalized current Insights/SLE-trend responses. No extra routes are admitted from the HPE candidate names. The coverage gate must report these limits and distinguish request-wire/synthetic proof from vendor-response proof; it must not award verified feature coverage merely because a generated fixture passes.
