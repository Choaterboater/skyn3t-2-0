# Supabase Next.js Scaffold Variant — Design

## Goal

Teach SkyN3t to produce a useful Supabase-shaped Next.js starter when a brief asks for Supabase auth, database, or backend features, without adding a new stack or requiring a live Supabase account during tests.

## Context

SkyN3t already treats app-specific product shapes as scaffold variants when they share an existing stack's runtime and proof path. Supabase fits the existing `nextjs` stack: it is still a Next.js App Router project, but it needs a Supabase client helper, safe browser env vars, and visible generated UI that explains whether Supabase is configured.

The repo currently has no first-class Supabase variant. The only existing Supabase reference is a benign browser-exposed-key guard test for `NEXT_PUBLIC_SUPABASE_URL`.

## Options Considered

### Option A: Add a new `supabase` stack

This would expose Supabase as a separate builder vocabulary entry. It is too broad for the current need: it would require planner, selector, proof, gate, docs, and registry updates even though the runtime is just Next.js.

### Option B: Add dashboard-level Supabase credentials

This would let users save Supabase project credentials in SkyN3t settings. It is useful later, but it does not improve generated app shape on its own and introduces secret-management surface before the scaffold needs it.

### Option C: Add a Next.js scaffold variant

This keeps Supabase as a content variant of the existing `nextjs` stack. Trigger on specific Supabase phrases, emit a runnable App Router project with `@supabase/supabase-js`, and rely on existing config detection/packaging flows to surface env vars.

Decision: use Option C.

## Scope

In scope:

- A phrase-gated `_implies_supabase(...)` helper with multi-word triggers only.
- A `nextjs` scaffold variant generated by `scaffold_for("nextjs", ..., brief)`.
- A runnable offline App Router project that includes:
  - `package.json` with `next`, `react`, `react-dom`, and `@supabase/supabase-js`.
  - `lib/supabaseClient.js` that reads `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
  - `app/page.jsx` that renders useful configured/unconfigured states without making network calls during build.
  - `app/layout.jsx`, `app/globals.css`, `next.config.js`, `jsconfig.json`, `.gitignore`, and `README.md`.
- Brief-side config detection for Supabase client keys:
  - `NEXT_PUBLIC_SUPABASE_URL`, kind `url`, scope `client`.
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY`, kind `api_key`, scope `client`.
  - If the brief explicitly mentions service-role/admin/server Supabase access, add `SUPABASE_SERVICE_ROLE_KEY`, kind `secret`, scope `server`.

Out of scope:

- Connecting to a live Supabase project.
- Writing dashboard settings for Supabase credentials.
- Adding Supabase migrations, SQL generation, or auth callbacks.
- Adding a new proof gate.

## Trigger Rules

The trigger must use multi-word phrases to avoid stealing ordinary database or auth briefs. Examples that should trigger:

- `Supabase auth`
- `Supabase database`
- `Supabase backend`
- `Supabase project`
- `Supabase login`
- `Supabase dashboard`

Examples that should not trigger:

- `a database-backed Next.js app`
- `an auth dashboard`
- `a Firebase auth app`
- `a static Supabase pricing page` if the selected stack is not `nextjs`

## Data Flow

1. Planner/common stack selection continues choosing `nextjs` for Next.js or server-side web briefs.
2. `scaffold_for("nextjs", app_name, brief)` checks `_implies_supabase(brief)` before the base Next.js builder.
3. The Supabase variant returns the same Next.js scaffold contract plus Supabase-specific files and dependencies.
4. `detect_from_brief(...)` predicts Supabase env keys before generation.
5. Existing code-scan config detection also sees the generated env reads.
6. Packaging/settings UI flows receive the merged `ConfigSpec` without special routing.

## Error Handling

The generated app must not crash when env vars are absent. `lib/supabaseClient.js` exports both the env values and a nullable client. The page renders a setup state when `supabaseClient` is null and a configured state when both public vars are present.

No generated code should read or expose `SUPABASE_SERVICE_ROLE_KEY` in browser code.

## Testing

Add focused tests for:

- Trigger matches Supabase phrases and ignores generic auth/database briefs.
- A Supabase Next.js brief gets the variant files/dependency/client helper.
- A plain Next.js brief remains unchanged.
- The variant passes the existing Next.js structural proof.
- Brief-side config detection emits the two public Supabase keys as client config.
- Service-role/admin Supabase briefs add the server-scoped service-role key.

## Success Criteria

- Normal Next.js scaffolds are unchanged.
- Supabase Next.js briefs produce a runnable, inspectable scaffold with safe missing-config behavior.
- Config detection surfaces the Supabase keys without a live Supabase account.
- Focused tests pass under the managed sandbox and the broader scaffold/config suites remain green.
